## Vue d'ensemble

**BuildWithUS** (nom de code interne `BuildWithUse`) est une plateforme permettant à des équipes marketing/produit de **concevoir, personnaliser et exporter des templates d'e-mails HTML/MJML** via un éditeur visuel, avec :

- un **éditeur drag-and-drop** basé sur des blocs (Next.js + `@dnd-kit` + Monaco + Tiptap) ;
- une **assistance IA** pour générer des palettes de couleurs, mapper des variables et proposer des blocs de contenu ;
- une **gestion multi-tenant** complète (organisations, invitations, rôles, quotas d'usage) ;
- une **facturation Stripe** (checkout, webhooks, abonnements) ;
- une **API publique** pour les développeurs tiers (clients API, tokens, sessions de builder embarquées) ;
- un **export PDF** et un rendu MJML → HTML côté serveur (Playwright).

Le projet est organisé en **monorepo multi-services** : un frontend Next.js, trois microservices NestJS/Python et un pipeline utilitaire, orchestrés derrière une passerelle API unique.

                          │  └──────┬───────┘  └───────┬───────────┘    │
                          │         │                  │                │
                          │         └────────┬─────────┘                │
                          │            ┌──────▼──────┐                  │
                          │            │ PostgreSQL   │                  │
                          │            │ (managée)    │                  │
                          │            └─────────────┘                  │
                          │                                              │
                          │  ┌──────────────────┐  ┌──────────────────┐│
                          │  │ ai-template-      │  │ image-pipeline   ││
                          │  │ service (FastAPI) │  │ (FastAPI)        ││

> Le rendu conversationnel de génération IA (chat de construction de blocs) est géré côté **frontend** via la route `/api/ai/chat` (Vercel AI SDK), qui appelle un serveur vLLM interne. `ai-template-service` ne gère que les helpers IA non conversationnels (palettes de couleurs, mapping de variables/champs de facture).

### Détail des services

| Service | Rôle | Techno | Port local (défaut) |
|---|---|---|---|
| **frontend** | Éditeur, dashboard, checkout, portail développeurs, embed public | Next.js 16 / React 19 | `3001` |
| **api-gateway** | Point d'entrée unique, agrégation, auth guard JWT, Stripe, e-mails, rendu PDF/MJML, stockage médias | NestJS | `3000` |
| **auth-service** | Authentification, tenants, invitations, rôles, quotas, API clients développeurs | NestJS + TypeORM + PostgreSQL | `3003` |
| **template-service** | CRUD templates, variables tenant, favoris, duplication (CQRS commands/queries) | NestJS + TypeORM + PostgreSQL | `3002` |
| **ai-template-service** | Suggestion de palettes, mapping variables ↔ colonnes de fichier | FastAPI (Python) | `8001` |
| **image-pipeline** | Proxy de recherche d'images libres (remplace l'ancien pipeline MinIO/ChromaDB) | FastAPI (Python) | `8002` |
| **packages/shared-kernel** | Code partagé (config, logger, intercepteurs) consommé par `template-service` | TypeScript (package local `file:`) | — |
| **packages/proto** | Contrats Protobuf partagés (commands/queries templates, types communs) | Protocol Buffers | — |

> **Note d'architecture — communication inter-services :** les contrats `.proto` (CQRS `TemplateCommandService` / `TemplateQueryService`, `AuthService`) définissent le schéma des échanges, mais en production les services communiquent aujourd'hui **en HTTP/REST** entre eux (`fetch` côté `api-gateway` vers `AUTH_SERVICE_URL` / `TEMPLATE_SERVICE_URL`). Le gateway conserve une compatibilité descendante qui réécrit automatiquement les anciennes URLs gRPC (`:50055`, `:50054`) vers leurs équivalents HTTP (`:3003`, `:3002`) — utile si d'anciennes variables d'environnement gRPC traînent encore quelque part.

### Pattern applicatif

- `auth-service` et `template-service` suivent une architecture **hexagonale / DDD** : `domain/` (entités, règles métier) → `application/` (cas d'usage, CQRS) → `infrastructure/` (TypeORM, contrôleurs HTTP).
- `template-service` sépare explicitement **Commands** (`CreateTemplate`, `UpdateTemplate`, `DeleteTemplate`, `DuplicateTemplate`, `ToggleFavorite`, gestion des variables tenant) et **Queries** (`GetTemplate`, `ListTemplates`, `GetPopularTemplates`, `RenderTemplate`, `GetTenantVariables`).
- `api-gateway` reste volontairement fin : contrôleurs (`auth`, `billing`, `media`, `super-admin`, `template`) + services clients HTTP vers les microservices internes.

## Démarrage en local

### 1. Cloner et installer

```bash
git clone https://github.com/mohamedazizsaid/BuildWithUS.git
cd BuildWithUS

# Backend — un install par service
cd auth-service && npm ci && cd ..
cd template-service && npm ci && cd ..
cd api-gateway && npm ci && cd ..

# Services Python (environnement virtuel partagé conseillé à la racine, .venv/)
python -m venv .venv
source .venv/bin/activate            # Windows : .venv\Scripts\activate
pip install -r ai-template-service/requirements.txt
pip install -r image-pipeline/requirements.txt

# Frontend
cd frontend && npm ci && cd ..
```

### 2. Configurer les variables d'environnement

Copiez `api-gateway/.env.example` vers `api-gateway/.env` et complétez les clés (voir [Variables d'environnement](#variables-denvironnement)). Faites de même pour chaque service qui en a besoin (`auth-service`, `template-service`, `ai-template-service`, `image-pipeline`, `frontend`).

### 3. Lancer tous les services

**Windows (PowerShell) :**

```powershell
./start-all.ps1
```

**Windows (cmd) :**

```bat
start-all.bat
```

**macOS / Linux (manuel, un terminal par service) :**

```bash
cd auth-service && npm run start:dev            # http://localhost:3003
cd template-service && npm run start:dev        # http://localhost:3002
cd api-gateway && npm run start:dev             # http://localhost:3000
cd ai-template-service && uvicorn app.main:app --reload --port 8001
cd image-pipeline && uvicorn search_api:app --reload --port 8002
cd frontend && npm run dev                      # http://localhost:3001
```

L'application est ensuite accessible sur **http://localhost:3001**, avec toutes les requêtes API passant par `api-gateway` sur `http://localhost:3000`.

## Variables d'environnement

Les secrets ne sont **jamais commités**. Le fichier de référence est [`api-gateway/.env.example`](api-gateway/.env.example).

| Variable | Service | Description |
|---|---|---|
| `PORT` | tous | Port d'écoute HTTP (Render l'injecte automatiquement en prod) |
| `FRONTEND_ORIGIN` | api-gateway, ai-template-service | Origine(s) autorisée(s) en CORS (URL Vercel) |
| `AUTH_SERVICE_URL` / `TEMPLATE_SERVICE_URL` | api-gateway | URLs internes des microservices |
| `AI_TEMPLATE_SERVICE_URL` / `IMAGE_PIPELINE_URL` | api-gateway | URLs des services IA/images |
| `JWT_SECRET` | api-gateway, auth-service | Secret JWT — **doit être identique** entre les deux services |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` | auth-service, template-service | Connexion PostgreSQL (injectées par Render depuis la base `buildwithus-db`) |
| `DB_SYNC` | auth-service, template-service | Synchronisation auto des entités TypeORM (`true` en environnement géré) |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `STRIPE_TAX_RATE_ID` / `STRIPE_RETURN_URL` | api-gateway | Facturation Stripe (clés **live**, jamais de clés test en prod) |
| `RESEND_API_KEY` / `EMAIL_FROM` | api-gateway | Envoi d'e-mails transactionnels (Resend + templates MJML) |
| `CLOUDINARY_URL` | api-gateway | Stockage médias principal (gratuit, sans carte bancaire) |
| `MINIO_ENDPOINT` / `MINIO_PORT` / `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` / `MINIO_BUCKET` | api-gateway | Stockage de secours (S3-compatible) |
| `OPENROUTER_API_KEY` / `AI_MODEL` | ai-template-service | Accès au modèle IA (`deepseek/deepseek-v3.2` via OpenRouter) |
| `PEXELS_API_KEY` | image-pipeline | Accès à l'API de recherche d'images Pexels |
| `NEXT_PUBLIC_API_URL` | frontend | URL publique de l'`api-gateway` |
| `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` | frontend | Clé publique Stripe |
| `NEXT_PUBLIC_APP_URL` | frontend | URL publique du frontend (callbacks, embed) |

## Contrats inter-services (Protobuf)

Le dossier [`packages/proto`](packages/proto) définit les contrats de données partagés, organisés par responsabilité :

- **`common.proto`** — types communs (health check, pagination, etc.)
- **`template_commands.proto`** — `TemplateCommandService` : `CreateTemplate`, `UpdateTemplate`, `DeleteTemplate`, `DuplicateTemplate`, `ToggleFavorite`, `UpdateTenantVariables`, `AddTenantVariable`, `DeleteTenantVariable`
- **`template_queries.proto`** — `TemplateQueryService` : `HealthCheck`, `GetTemplate`, `ListTemplates`, `GetPopularTemplates`, `RenderTemplate`, `GetTenantVariables`
- **`auth-service/proto/auth.proto`** — `AuthService` : inscription/connexion, gestion des invitations, profils, quotas tenant, clients API développeurs, sessions builder embarquées, actions super-admin

Ces schémas documentent le contrat métier entre services et servent de source de vérité, même si le transport actuel entre `api-gateway` et les microservices internes est du **HTTP/REST** (voir [Architecture](#architecture)).

## Qualité de code & tests

- **Linting** : ESLint (services TypeScript) + Flake8/Ruff (services Python), exécutés sur chaque push et chaque pull request.
- **Tests unitaires** : Jest avec couverture (`npm run test:cov`) sur `auth-service`.
- **Analyse continue** : [Qlty Cloud](https://qlty.sh) agrège lint, duplication de code, analyse de sécurité basique (Semgrep) et seuils de complexité (`.qlty/qlty.toml`) :
  - complexité cyclomatique max par méthode : `10`
  - longueur max d'une méthode : `50` lignes
  - complexité max par fichier : `55`
  - nombre max d'arguments par fonction : `6`
- La couverture de `auth-service` est uploadée vers Qlty Cloud via OIDC (aucun secret stocké côté GitHub si OIDC est activé).

## CI/CD

Deux workflows GitHub Actions pilotent l'intégration et le déploiement continus :

### [`pr-checks.yml`](.github/workflows/pr-checks.yml) — sur chaque Pull Request

1. **Détection des changements** (`dorny/paths-filter`) : identifie quels services sont impactés par la PR.
2. **Lint** : ESLint sur `api-gateway`, `auth-service`, `template-service`, `frontend` ; Flake8 sur `ai-template-service` et `image-pipeline`.
3. **Tests & couverture** : tests Jest de `auth-service`, upload vers Qlty Cloud.
4. **Résumé automatique** : un commentaire est posté sur la PR avec le statut du lint et la liste des services modifiés.

*Aucun build Docker ni déploiement n'est déclenché sur une PR.*

### [`ci-cd.yml`](.github/workflows/ci-cd.yml) — sur chaque push vers `main`

```
detect-changes ──▶ lint-and-quality ──▶ docker-build-push ──▶ deploy-render
                └─▶ test ──────────────┘                  └─▶ deploy-vercel
```

1. **`detect-changes`** — filtrage par chemin pour ne traiter que les services modifiés (économie de minutes CI).
2. **`lint-and-quality`** — lint complet TypeScript (4 services) + Python (2 services).
3. **`test`** — tests Jest + couverture, upload vers Qlty Cloud.
4. **`docker-build-push`** — build multi-service en matrice (`auth-service`, `api-gateway`, `template-service`, `ai-template-service`, `image-pipeline`), image poussée vers **GitHub Container Registry** (`ghcr.io/<owner>/<service>`), avec cache GHA pour accélérer les builds suivants.
5. **`deploy-render`** — déclenche un **Render Deploy Hook** dédié pour chaque service modifié (mise à jour indépendante, pas de redéploiement global inutile). `template-service` est redéployé également si `packages/**` change (dépendance partagée).
6. **`deploy-vercel`** — déclenche le **Vercel Deploy Hook** du frontend uniquement si `frontend/**` a changé.

Chaque run précédent sur la même branche est annulé automatiquement (`concurrency: cancel-in-progress`).

#### Secrets GitHub Actions requis

| Secret | Usage |
|---|---|
| `QLTY_COVERAGE_TOKEN` | Upload de couverture vers Qlty Cloud (optionnel si OIDC activé) |
| `RENDER_DEPLOY_HOOK_AUTH_SERVICE` | Déclenchement du déploiement `auth-service` |
| `RENDER_DEPLOY_HOOK_API_GATEWAY` | Déclenchement du déploiement `api-gateway` |
| `RENDER_DEPLOY_HOOK_TEMPLATE` | Déclenchement du déploiement `template-service` |
| `RENDER_DEPLOY_HOOK_AI_SERVICE` | Déclenchement du déploiement `ai-template-service` |
| `RENDER_DEPLOY_HOOK_IMAGE_PIPELINE` | Déclenchement du déploiement `image-pipeline` |
| `VERCEL_DEPLOY_HOOK_URL` | Déclenchement du déploiement `frontend` |
| `GHCR_TOKEN` | PAT `write:packages` pour pousser les images Docker (ou `GITHUB_TOKEN` si repo public) |

## Déploiement

Le déploiement complet est décrit pas à pas dans [`DEPLOY.md`](DEPLOY.md). Résumé :

### Backend — Render (Blueprint / Infrastructure as Code)

Le fichier [`render.yaml`](render.yaml) décrit l'ensemble de l'infrastructure backend :

| Ressource | Type | Détails |
|---|---|---|
| `buildwithus-db` | PostgreSQL managée | plan free, région `frankfurt`, base partagée par `auth-service` et `template-service` |
| `auth-service` | Web Service Docker | `auth-service/Dockerfile`, contexte `./auth-service` |
| `template-service` | Web Service Docker | `template-service/Dockerfile`, contexte racine (dépend de `packages/shared-kernel`) |
| `ai-template-service` | Web Service Docker | `ai-template-service/Dockerfile`, port `8001`, modèle `deepseek/deepseek-v3.2` |
| `image-pipeline` | Web Service Docker | `image-pipeline/Dockerfile`, port `8002` |

> `api-gateway` est déployé séparément sur Render (hors Blueprint) — voir `DEPLOY.md` pour la configuration manuelle et les variables sensibles (Stripe, Resend, Cloudinary/MinIO).

Étapes clés :
1. Render Dashboard → **New +** → **Blueprint** → sélectionner le repo → Render détecte `render.yaml` automatiquement.
2. Renseigner les secrets marqués `sync: false` (JWT, clés Stripe/Resend/Cloudinary/Pexels/OpenRouter).
3. Configurer le webhook Stripe (`/billing/webhook`) avec les événements `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`.
4. Exécuter les migrations TypeORM après le premier déploiement (`npm run migration:run` dans `auth-service` et `template-service`, avec `DATABASE_URL` de Render).

### Images Docker de production

Chaque service dispose d'un **Dockerfile multi-stage** optimisé :

- `auth-service`, `api-gateway` : build TypeScript (`node:20-bookworm-slim`) → runtime allégé avec utilisateur non-root.
- `api-gateway` embarque en plus les dépendances système Playwright/Chromium (rendu PDF headless).
- `ai-template-service`, `image-pipeline` : `python:3.12-slim`, dépendances via `requirements.txt`, exécution `uvicorn`, utilisateur non-root.

### Frontend — Vercel

1. **New Project** → sélectionner le repo `BuildWithUS` → **Root Directory** : `frontend` → framework Next.js détecté automatiquement.
2. Configurer `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_APP_URL` dans les variables d'environnement Vercel (environnement Production).
3. Domaine personnalisé optionnel via **Settings → Domains**.

### Stockage médias — Cloudinary

Solution de stockage par défaut (gratuite, sans carte bancaire, CDN mondial inclus). Configuration en 3 étapes dans `DEPLOY.md` : créer un compte, copier la variable d'environnement API, la coller comme `CLOUDINARY_URL` dans Render. `MINIO_*` reste disponible comme solution de repli S3-compatible.

### Checklist avant mise en production

- [ ] Tous les services Render sont **Live**
- [ ] Variables sensibles configurées (Stripe, Resend, stockage)
- [ ] Webhook Stripe configuré et testé
- [ ] Migrations DB exécutées
- [ ] Build Vercel réussi, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` en clé **live**
- [ ] Flux complet testé en production : inscription → template → génération IA → checkout
